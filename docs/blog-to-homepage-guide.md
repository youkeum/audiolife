# 네이버 블로그 → AudioLife 게시글 이식 가이드

최종 정리: 2026-10-20. 이 문서는 블로그에 먼저 발행한 글을 홈페이지의 현재 양식으로 옮기는 전용 작업창의 시작 문서입니다.

## 1. 작업 목적과 시작 정보

- 블로그: https://blog.naver.com/audiolife-
- 홈페이지: https://audiolife.kr
- 프로젝트: `/Users/ykkim/Desktop/Homepage`
- 저장소: `youkeum/audiolife`, 운영 브랜치 `main`
- 기본 흐름: 사용자가 블로그에 발행 → 글 URL 전달 → 원문과 미디어 수집 → 홈페이지 양식으로 편집 → 로컬 확인 또는 커밋·푸시 → 결과 기록.
- 새 작업창을 준비하는 시점에는 가이드만 읽고 다음 글 URL을 기다립니다. 과거 글을 임의로 다시 이식하지 않습니다.
- 사용자가 URL과 함께 “홈페이지에 올려 줘/이식해서 업로드해 줘”라고 요청하면 해당 글의 변환, 검증, 커밋·푸시까지 진행합니다. Vercel 배포 상태와 운영 페이지는 사용자가 별도로 요청할 때만 확인합니다. “초안/로컬에서 확인” 요청이면 로컬 원고까지 준비합니다.
- 기간이나 여러 URL을 지정하면 그 범위만 처리합니다. 날짜 경계가 모호해 대상이 달라지는 경우에만 확인합니다.

## 2. 작업 전에 읽을 파일

1. `docs/content-authoring.md`: 공통 원고 편집 기준.
2. `content/reviews/_template.md`: 제품 리뷰 템플릿.
3. `content/reviews/_space-template.md`: 공간 리뷰 템플릿.
4. `content/articles/_template.md`: 소식·기사 템플릿.
5. `docs/blog-import-log.md`: 이식 기록과 중복 여부.

현재 양식의 실제 예시는 아래 세 편입니다. 예시의 문장을 복사하는 것이 아니라 문단 구성과 메타데이터 사용을 참고합니다.

- 제품 리뷰: `content/reviews/naver-224441108934.md` (PD5).
- 공간 리뷰: `content/reviews/naver-224437065078.md` (천변풍경).
- 기사: `content/articles/naver-224443570659.md` (소니 워크맨).

`AGENT.md`는 Git 훅이 자동 갱신하는 프로젝트 개요입니다. 지속적으로 유지할 이식 규칙은 이 가이드에 기록합니다.

## 3. 대상 확인과 원문 수집

1. `git status --short --branch`로 기존 변경을 확인합니다. 다른 작업창의 변경을 덮어쓰거나 함께 커밋하지 않습니다.
2. 블로그 글의 실제 제목, 최초 발행일, 분류, 전체 본문, 사진 순서, 캡션, 링크, 영상, 해시태그를 읽습니다. 목록의 미리보기나 검색 결과만으로 본문을 재구성하지 않습니다.
3. 연결된 브라우저/Aside가 필요한 경우 해당 도구의 사용 가이드를 먼저 읽고 사용합니다. 로그인 세션을 사용할 수 없으면 공개 원문 접근을 시도하고, 여전히 본문을 볼 수 없을 때만 필요한 원문을 요청합니다.
4. 네이버 글 번호와 원본 URL을 확인합니다. 같은 글의 모바일·PC 주소는 같은 원문으로 취급합니다.
5. `docs/blog-import-log.md`, `content/reviews`, `content/articles`에서 글 번호·제목·제품명으로 기존 이식 여부를 검색합니다. 기록에 없더라도 이미 게시된 파일이 있을 수 있습니다.
6. 같은 글이 이미 있다면 해당 파일을 갱신하고 URL을 유지합니다. 새 파일을 만들어 중복 발행하지 않습니다.

새 네이버 글의 기본 파일명은 `naver-<글번호>.md`입니다. 기존에 다른 파일명으로 게시한 글은 그 파일명을 유지합니다.

## 4. 분류와 경로

| 블로그 분류/내용 | 원고 위치 | 홈페이지 주소 | 이미지 폴더 |
| --- | --- | --- | --- |
| 오디오 소식 | `content/articles/<slug>.md` | `/articles/<slug>` | `public/posts/articles/<slug>/` |
| 오디오 리뷰 | `content/reviews/<slug>.md` | `/reviews/<slug>` | `public/posts/reviews/<slug>/` |
| 청음 공간 방문 리뷰 | `content/reviews/<slug>.md` | `/reviews/<slug>` | `public/posts/reviews/<slug>/` |

`category`는 메뉴 분류와 별개인 제품군입니다. `DAP`, `DAC`, `HEADPHONE`, `EARPHONE`, `TURNTABLE`, `SOFTWARE`, `LISTENING SPACE` 등 현재 원고의 표기를 우선 재사용합니다. 기존 과거 분류를 이번 작업에서 일괄 변경하지 않습니다. 컬럼은 별도 요청이 있을 때 컬럼 작성 가이드를 따릅니다. 캘린더는 사용하지 않습니다.

## 5. 본문 편집 원칙

- 원문의 의미, 말투, 평가, 수치, 비교 조건, 사진 순서를 보존합니다. 분량을 줄이기 위한 요약 재작성이나 경험·평가의 추가는 하지 않습니다.
- `title`에는 실제 브랜드·모델 또는 공간명이 드러나도록 정리하되 원래 제목의 개성을 유지합니다.
- `excerpt`는 본문과 별도로 작성한 1~2문장 요약입니다. 대략 70~130자를 편집 기준으로 삼되 분량을 억지로 맞추지 않습니다. 본문 첫 문단을 그대로 복사하지 않습니다.
- 주제가 전환되는 곳에 의미 있는 `## 소제목`을 넣습니다. 필요한 경우에만 `###`를 사용합니다. 원문에 없는 내용을 채워 넣어 템플릿의 모든 항목을 만들지 않습니다.
- 제목은 페이지가 H1으로 출력하므로 본문에 `# 글 제목`을 중복 삽입하지 않습니다.
- 블로그 UI, 이웃 추가, 공유 버튼, 댓글, 공감 수, 편집기 안내 문구는 본문에서 제외합니다. 캡션과 원문에 포함된 출처 표시는 보존합니다.
- 본문 끝의 해시태그/태그 목록은 본문에서 삭제하고 `tags`로 옮깁니다. `#`를 제거하고 중복·동일 브랜드 표기를 정리합니다. 의미 있는 원문 태그는 개수 제한 때문에 버리지 않습니다. `오디오 리뷰`, `오디오 소식`, `리뷰`, `기사`처럼 메뉴가 이미 표현하는 일반 분류명은 중복 태그에서 제외합니다.
- 원문의 숫자·색상 표기 등 일반 문장에 포함된 `#`는 해시태그로 오인해 삭제하지 않습니다.
- 기존 홈페이지 글에 대한 언급은 해당 글이 실제 존재하고 문맥에 도움이 될 때 내부 링크로 연결합니다. 관련 글 섹션은 사이트가 자동 생성하므로 본문 끝에 반복해서 만들지 않습니다.
- 청음 환경, 직접 구매·대여·제공 여부, 측정치, 가격·출시일은 원문에 있는 사실만 사용합니다. 원문 발행 당시의 “오늘/다음 달”을 이식하는 날 기준으로 바꾸지 않습니다. 명확한 경우 원문 날짜를 기준으로 절대 날짜로 풀어 씁니다.
- 사실관계를 추가 확인하거나 수정해 달라는 요청이 있으면 해당 내용의 공식 자료를 확인하고 수정 내용을 기록합니다. 일반 이식만 한 경우 새 사실 검증까지 완료했다고 보고하지 않습니다.

## 6. Frontmatter

현재 파서에서 사용하는 키만 게시용 메타데이터로 기대합니다. 원본 URL·이식 기록은 아래 운영 기록에 남깁니다.

```yaml
---
title: "브랜드 제품명 리뷰: 핵심 인상"
date: "2026-10-20"
excerpt: "실제로 다룬 내용과 비교의 초점을 별도 문장으로 요약합니다."
category: "DAP"
tags: ["DAP", "브랜드명", "모델명"]
reviewItemType: "Product"
reviewItemName: "실제 브랜드 모델명"
---
```

- `date`: 원문의 최초 발행일. 홈페이지 이식일로 덮어쓰지 않습니다.
- `updated`: 발행 후 실제 내용을 수정·정비한 경우에만 실제 날짜를 기록합니다. 새 글을 같은 날 이식하는 경우 중복 수정일은 필요 없습니다. 이식 작업일 자체는 운영 기록에 남깁니다.
- 리뷰어는 YK로 자동 표시되므로 `author`나 본문 서명을 추가할 필요가 없습니다.
- 제품 리뷰의 `reviewItemType`은 `Product`, 공간 리뷰는 `Place`입니다. `reviewItemName`은 제목 전체가 아니라 실제 대상명입니다. 현재 소프트웨어·서비스 사용기는 기존 리뷰 예시를 참고합니다.
- 기사는 `reviewItemType`, `reviewItemName`을 넣지 않습니다.
- `coverImage`는 선택 사항입니다. 생략하면 첫 Markdown 이미지를 대표 이미지로 사용하고 상세 본문에서 중복 표시를 줄입니다. 대표 이미지를 달리 지정할 때만 실제 로컬 경로를 넣습니다.
- 검색용 구조화 데이터와 canonical은 사이트 코드가 생성합니다. 원고에 JSON-LD, 별점, 임의 가격, 별도 canonical 코드를 삽입하지 않습니다.

## 7. 사진·영상 처리

1. 블로그 원문의 콘텐츠 이미지를 실제 파일로 확보하고 위 이미지 폴더에 저장합니다. URL이 아니라 실제 파일의 형식에 맞는 확장자를 사용합니다. 로그인 페이지나 오류 응답을 이미지로 저장하지 않습니다.
2. 가능하면 원문 고해상도 자산을 사용합니다. 새 이름은 `1.jpg`, `2.png`처럼 순서를 파악하기 쉽게 정하고, 실제 내용과 순서를 유지합니다. 무관한 사진, AI 대체 이미지, 장식 프레임을 추가하지 않습니다.
3. 본문 경로에는 `public`을 쓰지 않습니다. 예: `![제품 전면과 조작 버튼](/posts/reviews/naver-글번호/1.jpg)`.
4. alt는 실제 이미지와 문맥을 보고 짧게 작성합니다. 모든 사진에 제목을 반복하지 않습니다. 같은 파일이 원문에서 반복되는 경우 파일은 재사용해도 본문상의 배치는 유지합니다.
5. 사진의 시각적 내용은 보존하되 기존 커밋 훅의 크기·용량 최적화는 적용됩니다. 픽셀 단위의 원본 보존과 동일한 의미가 아닙니다. GIF·동영상을 정지 이미지로 임의 변환하지 않습니다.
6. YouTube는 단독 URL로 두면 기존 임베드가 동작합니다. 원문 네이버 영상을 확보하거나 지원 방식으로 삽입할 수 없으면 원문 영상 링크를 남기고 완료 보고에 대체 사실을 명시합니다. 누락을 숨기지 않습니다.
7. 본문의 단독 일반 URL은 기존 링크카드 처리를 사용합니다. 미리보기 실패 시 링크 버튼으로 표시됩니다.
8. 이미 게시된 사진을 교체하면 새 파일명을 사용해 이미지 변환 캐시를 피합니다. 게시된 글의 slug는 변경하지 않습니다.

이미지 치수는 `node scripts/generate-image-dimensions.mjs`로 갱신합니다. `npm run build`의 prebuild에서도 자동 실행됩니다. 생성된 `lib/image-dimensions.json`은 코드와 함께 관리합니다. 서버 요청마다 원본 이미지의 치수를 읽는 방식으로 되돌리지 않습니다. 이 방식은 전체 미디어를 Vercel 함수에 포함시켜 용량 제한으로 배포가 실패했던 원인입니다.

## 8. 확인과 게시

1. 해당 글의 원문과 변환본을 비교해 문단·사진·캡션·영상·링크가 빠지지 않았는지 확인합니다. 원문 문체와 내용은 보존하면서 요약·소제목·태그만 정리되었는지 검토합니다.
2. 새 미디어가 있으면 치수 목록을 생성하고, 로컬 초안 요청이면 `npm run dev`에서 해당 글 주소를 전달합니다.
3. 게시 전 `npm run content:check`와 `npm run build`를 실행합니다. 코드 변경을 동반하면 영향 범위에 맞는 테스트도 실행합니다. 기존 원고의 편집 권고를 이번 작업에서 전부 수정할 필요는 없습니다. 새 글의 오류와 새로 발생한 오류는 해결합니다.
4. 사용자가 이미 페이지 확인을 마쳤고 재점검 생략을 요청했다면 전체 페이지 브라우저 순회를 반복하지 않습니다. 커밋·푸시 전에는 로컬 빌드 성공을 확인합니다.
5. `git diff`와 스테이징 목록을 확인하고 해당 원고, 미디어, 이미지 치수 목록, 이식 기록을 커밋합니다. “모두 커밋” 요청이 없는 한 다른 작업의 변경을 섞지 않습니다. `AGENT.md`는 훅에서 자동 갱신됩니다.
6. 커밋 훅이 새 이미지를 최적화할 수 있습니다. 커밋 후 치수 생성기를 실행해 목록이 달라졌다면 생성 파일을 후속 커밋합니다. Vercel 빌드에서도 최종 자산 기준으로 다시 생성됩니다. 기존 커밋을 임의 amend하지 않습니다.
7. `main`을 원격에 푸시합니다. 기본 작업은 여기서 마칩니다. 이식 기록에는 `푸시 완료·배포 미확인`으로 남기고, 푸시 성공을 실제 사이트 반영 완료로 표현하지 않습니다.
8. 사용자가 배포 확인을 별도로 요청한 경우에만 해당 커밋의 Vercel 상태를 확인합니다. 배포 성공 후 실제 `https://audiolife.kr/<articles 또는 reviews>/<slug>`에서 새 내용과 대표 이미지·본문 이미지 응답을 확인합니다. 오류가 있다면 원인을 수정해 후속 커밋으로 반영합니다.
9. 완료 보고에는 글 제목·예상 게시 주소, 처리한 사진 수, 영상 등 대체 처리 사항, 커밋 번호, `푸시 완료·배포 미확인` 상태를 짧게 적습니다. 별도 배포 확인까지 진행한 경우에만 그 결과를 보고합니다.

## 9. 이식 기록과 유지관리

`docs/blog-import-log.md`에 원본 URL, 홈페이지 경로, 원문 발행일, 작업일, 이미지 수, 상태, 예외를 기록합니다. 기본 상태는 푸시 후 `푸시 완료·배포 미확인`이며, `게시 완료`는 배포와 운영 페이지를 실제 확인한 경우에만 사용합니다. 파일명과 원문 글 번호는 중복 이식을 막는 기준입니다. 기존 이력은 추정해서 채우지 않습니다.

원고만 추가하는 작업에서 레이아웃·인증·SEO 코드·과거 글 전체를 함께 변경하지 않습니다. 양식이 바뀌면 이 가이드와 공통 템플릿을 같이 갱신합니다.
